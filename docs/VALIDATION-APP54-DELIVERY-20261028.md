## 为什么需要

在应用 53 上，用户点“全部标为已读”后停在 92/95，提示“请求被拒绝或服务暂不可用”。edge 对所有 API 请求有每分钟 120 次的全局限流；7 页收件箱、95 次已读请求，再加上电话页每 2 秒一次的轮询，超过了上限，服务端返回 429。应用 54 改为每秒最多标记 1 条；单条被拒绝时，等 61 秒后对同一条重试一次，再失败才停下，并显示进度。限流本身没有改。

## 过程与结果

- **构建**（在电脑的 WSL 中，不用 NAS）：ARM 程序 11 个；原生音频组件在 QEMU 上通过 33 项 ARM 测试。
- **本地回归**：fmt、整仓严格 Clippy 通过；整仓 642 通过、10 失败。其中 7 项与以往相同，都是已知的 WSL 环境问题。另外 3 项是 compat 的 `history_recovery_tests`，报错是 `PoisonError`：缺 Go 的那个测试失败时，会“毒化”同一个 crate 里共用的测试锁，后面拿这把锁的测试会跟着失败，波及几项取决于执行顺序。单独重跑 `history_recovery`，7 项全部通过。网页测试 16/16，进度工具测试通过。
- **签名与校验**：签名为格式 2 的 6 文件应用组，用设备现有信任密钥签名；用真实 ARM 更新器验签通过，3 个反例都被拒绝。
- **设备**：只读预检 → 上传并在设备上验证 → 停机持锁业务备份（数据库完整性通过，旧应用组已恢复运行）→ 暂存并回读 → 选择启动一次 → 健康检查 → 确认。所有步骤都一次通过；这次统一用 `PYTHONUTF8=1` 运行，避开了应用 53 时的编码问题。
- **结果**：floor 和 confirmed 都是 54；14 个 HTTPS 资源与源码一致；身份和所有者、95 条短信、未知回执不变；音频 7/7；转发关闭，已保存的 Bark 配置保留；普通数据关闭；出厂档位和自动恢复预算都没有动用。
