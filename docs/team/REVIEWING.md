# 主线审核与更新步骤

1. 核对PR作者、任务书和文件范围；记录起始main与PR完整40位HEAD。只读审查未完成前，不将PR中的安装/Root脚本放到设备上执行。
2. 阅读生产代码和对应测试，确认没有新权限、隐式联网、生产数据、超范围依赖或虚构成功。运行与修改相称的隔离检查，失败和未运行项如实保留。
3. 按完整HEAD写结论：需修改、离线范围通过或全范围验收；明确哪些STAT/NET步骤通过，哪些仍需主线/设备。
4. 将真实记录加入 `reviews.json`。它由负责人维护；下面只是结构示例，不是一次真实验收。

```json
{
  "member_id": "member-a",
  "pr": 123,
  "head": "替换为被审核的完整40位十六进制HEAD",
  "decision": "offline_accepted",
  "steps": ["A-01", "A-02"],
  "evidence": ["docs/deliveries/member-a-usage-stats.md"],
  "self_reported_hours": null
}
```

5. 合并时保留真实作者和来源，不将两位的代码重新署名为负责人。主线集成需要的改动独立提交，便于区分开发、修复和合并工作。
6. 核对main后 `git fetch origin`，运行 `python tools/progress/team.py --ref origin/main`。脚本读取当前PR HEAD，变更后自动显示需复审；没有审核记录时，CI成功/已经合并仍显示未关联验收。
7. 用原台账维护脚本更新实际已经完成的项目动作；分支离线通过不能代替真实设备验收。重建并验证看板，提交，再确认Pages发布及线上数据。
8. 工程材料留存：任务书、交付报告、逐HEAD结论、提交/合并记录、版本说明和来源许可。权限邀请、实际授权核验另行记录；编辑roster不能代替GitHub设置。

成员自报工时只在对应HEAD已接受的范围内汇总。无填报为null，不用0冒充实际没有耗时。任务步骤去重计数，Git增删量/非空行仍分开显示。
