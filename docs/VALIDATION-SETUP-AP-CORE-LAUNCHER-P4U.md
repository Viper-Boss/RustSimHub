## 解决的问题

热点候选原来直接覆盖 Core 的启动命令。应用回退后，旧 Core 可能不认识新的联合热点参数；原厂16甚至不认识受管转发参数。可选配网功能因而可能妨碍电话和短信恢复。

新增 [core-launcher](../crates/core-launcher/src/lib.rs) 是有限、非 Root 的进程入口。它读取选定 Core 的构建信息，选择固定参数，然后以 `exec` 替换自身；没有常驻主管、命令执行 API、任意程序路径、联网或服务管理功能。

| 选定 Core | 允许的启动行为 |
|---|---|
| 实际核对过的原厂16源码归档 | 基本电话/短信模式 |
| 实际核对过的48源码归档 | 受管转发模式 |
| 实际核对过的49源码归档 | 两端热点契约均匹配时联合模式，否则受管转发 |
| 新构建，明确声明启动能力 | 只使用其声明的固定模式；热点仍须两端契约匹配 |
| 未知旧构建、开发夹具、错误架构或数据库版本 | 拒绝，不猜测参数 |

三个历史档位依据设备上各程序实际的 `--build-info` 确认；这些是公开软件归档摘要，不是设备或 SIM 标识。历史兼容范围仅限这三份已核对构建，不宣称支持任意旧版本。

## 接口与权限边界

- [Core 构建信息](../crates/core/src/main.rs) 新增 `service_launch`，格式1，固定能力为 `device`、`forwarding_managed`、`setup_ap`。它不改变业务接口、会话期限或派发权限。
- 启动器仅接受无参数启动或 `--build-info`。实际启动要求 UID/GID986；Core 路径、IPC UID、数据目录及热点通道均在程序中固定。
- [Linux 实现](../crates/core-launcher/src/linux.rs) 要求 Core 为 Root 所有的普通文件，拒绝符号链接、多硬链接、可被组/其他用户写入或带 setuid/setgid 的文件；不增加能力。
- 构建信息子进程使用空环境、空输入、有限输出及3秒截止；输出上限16384字节，退出和失败均回收子进程。临时读取不会进入 Core 业务服务流程。
- Root 热点契约上限4096字节，要求可信文件权限，按严格类型及唯一字段解析。文件缺失、损坏、不可读或不匹配时不启用热点，保留该 Core 支持的基础通信/受管转发。
- [Core drop-in](../firmware/system/setup-ap/50-setup-ap-core.conf) 改为固定启动器，不接受配置提供的命令。原服务的非 Root 身份、无能力、只读绑定及资源限额保持。

## 签名维护包和安装顺序

[打包器](../tools/setup_ap_package.py) 的独立热点维护包升级为格式2：八个固定目标，新增启动器程序；签名绑定 Core、Edge、热点程序、启动器四份实际程序的源码、摘要及契约。启动器协议必须为1，Core必须明确声明完整联合模式。普通应用包的信任域和格式不变。

[离线准入](../tools/system/setup_ap_install.py) 继续要求当前选定 Core/Edge 与维护包同源、已确认应用、业务空闲、备份回读及精确既有服务状态。新维护包必须完整包含启动器，拒绝旧七文件包和签名后的格式降级。原厂兼容并不意味着允许在任意旧系统上强行安装新维护包。

[固定安装脚本](../firmware/system/setup-ap/install.sh) 的交付清单为28文件，安装目标为八个：先发布程序、单元、契约及启动器，再完成实际离线材料准备，最后才发布两份激活配置。中断后只接受同一份精确内容；回退删除前先核对全部目标和暂存文件，保留身份、所有者及业务数据库。安装脚本仍不启动服务、不切网。
