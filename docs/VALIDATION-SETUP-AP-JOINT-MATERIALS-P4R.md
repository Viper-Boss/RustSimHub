## 补齐联合入口

`--serve-device-forwarding-managed-setup-ap` 同时启用现有短信转发管理与热点控制，保留 Edge/Core/worker 的独立 UID 和已有业务路径。新增固定 Core drop-in 使用 worker 983 及两个受保护槽；Root/Edge 单元仍为明确安装的候选，尚未放入自动启动的系统覆盖层。

`--prepare-device-ap-binding` 是离线维护命令：仅以非 Root 的 Core 身份导出真实设备公钥、realm 和 UID。它支持已有 Owner，保留 setup.used、原设置码和所有者，不生成新设置码或打开认领窗口。原 `--prepare-device-ap` 的首次设置限制保持。

Core、Edge 和热点程序现在都支持只读 `--build-info`，提供组件、架构、源码摘要和同一份联合契约。契约固定认证协议2、数据库6、应用格式2、父/试连/保存通道1、认领接管1、材料1、明确的两个运行模式和300秒最大窗口。契约源为 `firmware/system/setup-ap/contract.json`。

## 独立签名材料

`tools/setup_ap_package.py` 在维护主机创建、验证私有开发维护包，实际调用三份程序的元数据检查；可通过 QEMU 检查 AArch64。三者必须同源、同架构、相同契约并关闭开发夹具。Core/Edge 的精确摘要绑定在包中，程序仍属于原应用组。

维护签名域为 `RustSimHub.SetupApBundle.v1`，包外公钥验证；普通应用签名域不接受。七份固定载荷为热点程序、两个服务、tmpfiles、Core/target 两个 drop-in 和契约。目标路径、文件模式、架构、尺寸、摘要及已审查的服务字节全部固定，额外文件、改路径、重复字段、损坏、链接、混源、夹具或错误公钥拒绝。

该包为开发维护材料，私钥、实际包及原始验证记录仅保存在 `.private/`。本轮没有将新公钥加入设备或更新器，也没有拓宽普通应用更新的文件集合。设备安装前还须核对完整应用组、当前配置/备份、原文件和回退边界。
