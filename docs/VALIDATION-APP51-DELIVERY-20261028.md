# 应用 51 与灯控程序实机安装（2026-10-28）

用户授权安装，并选择“两个都装”：日常电话页的“确认未接来电”（#26，在 Edge 里，随签名应用组升级为 epoch 51），以及灯控降频（#25，灯控程序位于 rootfs，单独替换）。源码为 main `cddd2e4bb9169643caec44a63430de26c3a4af96`，导出包 SHA-256 为 `6cf17fa4177c1f54330eca40c6849ef7d47f98450f7336355bebf694ac36d615`，共 801 个文件。私有脚本和记录放在 `.local/*app51*`、`.private/app51-*`。

## 流程

沿用 10-26 安装应用 50 的同一套脚本，按 epoch 改写；有三处有意改动：

1. **连接**：原脚本经 NAS 口令跳板连接。改为直接使用用户批准的维护密钥，通过 Wi-Fi SSH 连接，主机指纹固定，并拒绝任何未知主机密钥。
2. **CI 门槛**：GitHub Actions 因账单停用，改用同一导出包在 WSL 上做的完整本地回归。结果：fmt 和整仓严格 Clippy 通过；整仓测试 641 通过、7 失败（都是已知的 WSL 环境失败：forwarder egress 5 个、需要 Go 的 compat 用例及其连带失败）；网页测试 16/16；进度工具测试通过。
3. **预检**：应用 50 已经安装了配网相关文件，所以预检从“要求这些路径不存在”改为“记录其存在”。

步骤：ARM 程序（11 个）和原生音频组件均在全新目录中从导出包编译，音频组件在 QEMU 上通过 33 项 ARM 测试 → 用设备现有信任对应的同一把开发签名密钥签名 epoch 51（6 个文件，22,293,049 字节） → 用真实 ARM 更新器在 QEMU 中验证，并确认错误密钥、损坏的 worker、旧 schema 都会被拒绝 → 设备只读预检 → 上传并在设备上验证，此时不安装 → 维护前置检查 → 停机持锁一致性备份 → 用设备上已安装的更新器暂存 → 重启应用组并选中候选 → 健康检查 → 确认。

## 中途失败一次（已恢复）

第一次备份时，`systemctl stop rustsimhub-app.target` 返回后，脚本立即检查各服务是否都已 inactive，检查失败，应用组就停在了停止状态。日志显示：目标单元 02:25:51.97（UTC）停止，经 PartOf 连带的各服务到 02:25:52.008 才停完；检查恰好落在这约 35 毫秒的间隙里，10-26 那次只是碰巧没撞上。当时还没有做备份、没有暂存，账本仍选中 epoch 50。随即启动应用组恢复到 epoch 50，并撤销了自动恢复定时器，**业务中断约 2 分钟**。修正方法是停止后最多等待 20 秒、反复检查直到所有服务都 inactive（备份和启动脚本都改了）。失败记录保留为 `*.failed-stop-race*`；另一次在连接前就因配置文件编码失败的预检记录也保留了下来。

## 结果

- 账本：floor 51，confirmed epoch 51（`f22b6680…`），没有候选，自动恢复预算未使用，出厂 16 保持不变。
- 健康检查：14 个 HTTPS 资源与 `cddd2e4` 源码逐字节一致（包括新增按钮的 `phone.js` 和 `index.html`），HTTPS 身份不变；Core、Edge、媒体都以非 Root 运行，没有有效 capabilities；一个所有者，69 条短信，受保护的业务表不变，音频通路 7/7，普通数据保持断开，转发保持关闭且已保存的 Bark 配置不变。
- 灯控：旧程序同时备份到设备（`/root/rustsimhub-app51-maintenance-20261028-first/status-led-before`）和本机私有目录，然后以原子方式替换 `/usr/libexec/rustsimhub/rustsimhub-status-led`，并只重启这一个服务。新程序的 `--build-info` 指向同一导出包。**各测 60 秒：灯控 CPU 从单核的 12.2% 降到 5.1%**，其中子进程部分从 11.6% 降到 4.6%；重启次数为 0。开机流程中没有任何检查固定这个程序的哈希。
- 最后的只读快照：没有失败的单元，10 个关键服务全部 active，Wi-Fi 已连接，蜂窝数据断开。
