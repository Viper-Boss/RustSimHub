# X1H：所有者短信转发配置页

2026-10-25。实际网页源码、Core IPC、本机服务链路和离线构建验证阶段。尚未部署到棒子，尚未做真实浏览器视觉或第三方推送验收。原 P0–P7 仍为 80%；X1、X2、X3 和 BLE 分别跟踪。

## 已实现的操作

首页原有四个测试入口保持简洁，新增默认折叠的“短信转发”区域。所有者显式登录、读取后，可配置 Webhook、Bark、Telegram，最多 8 个目标、32 条规则。规则支持发送方完全匹配、正文包含、SIM 代次、多个目标；默认仅发送新短信通知，完整正文需要明确选择并再次确认。邮件、正则、时间段和历史补发尚未实现。

总开关使用现有 `set_forwarding_enabled`。页面区分“已保存的开关意图”和经过有限 Root 服务核验的真实运行状态；未安装管理能力时只读，不显示虚假的“进程已停止”。没有自动轮询、自动保存或自动重试。重新开启默认只处理之后的新短信，不默默补发历史。

已有目标只返回 ID、发送器类型和凭据已隐藏标记。编辑规则默认发送 `{kind:"keep"}`，由 Core 按同一目标 ID 取回已有凭据。替换凭据需要明确勾选；新地址、token、key、chat ID 只放密码输入框，不写浏览器持久存储。提交、退出、页面隐藏、折叠配置和移除目标时清空输入。Core 继续验证最近登录所有者、完整规则、配置代次及请求 ID；保留凭据不能创建不存在的目标或跨所有者取值。

## 保存和失去确认

浏览器先用一个 IndexedDB 读写事务预留最小回执，再提交一次。回执只有格式、UUID、操作种类及预期配置代次，不含目标地址、凭据或短信正文。事务按当前请求 ID 比较，另一页已占用的保存槽不能覆盖，迟到响应不能清掉另一页的新记录。持久化失败时不会提交到设备。

新 `forwarding_request` 是所有者只读查询，精确返回某请求已应用的代次。记录库沿用有界请求历史；查不到可能是未受理、已清理或恢复造成，**不能当作未执行证明**。页面保留不确定记录，不重发。所有者可明确将其归档，再读取当前配置；归档不撤回旧请求。浏览器最多保留 64 份配置回执，优先淘汰已确认记录；全部不确定时停止新增，要求维护导出处理。

配置读取同时核对状态与规则代次；过期响应、重新登录、退出、配置并发变化均不能重新启用旧页面写入。递送列表分页展示短信/目标 ID 和排队、确认、失败、不确定等状态，不返回短信正文或凭据。

## 回归暴露的写锁问题

前两次完整回归分别在旧的存储关闭后重开测试遇到 `AlreadyOpen`，单独运行通过，失败记录保留。进一步用实际数据库线程复制锁文件描述符并延长其寿命，确定性复现：数据库已关闭，仍被保留的同一 open-file-description 导致锁未释放。原并行失败与这个机制一致，但没有抓取进程继承跟踪，不能声称已经证明原失败就是 fork 导致。

修正用 `WriterLock` 守卫显式解锁。只有成功取得排他锁后才创建守卫；`Database` 的 SQLite connection 字段先析构，然后锁守卫才释放。没有重试、忽略占锁或放开第二写者。新增测试同时证明活跃写者仍拒绝第二实例、旧句柄停止、重开将提交中操作恢复为 Unknown、旧复制描述符随后关闭不影响新写者的锁。Rust 字段按声明顺序析构，见 [Rust Reference](https://doc.rust-lang.org/reference/destructors.html)。
