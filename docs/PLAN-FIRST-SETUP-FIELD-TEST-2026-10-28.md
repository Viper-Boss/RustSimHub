# 首次配网实测方案：临时独立身份（2026-10-28，待用户批准）

用户选择用“临时独立身份”验证首次配网：**真实数据完全不动**，测试期间让正式服务临时改用一套全新的空数据，测完切回。本文是执行前的完整步骤，用户批准后才会动设备。

## 核心做法

不改正式服务的文件，只在 `/run/systemd/system/<服务>.d/` 下放**运行时覆盖配置**，让三个服务改用临时目录：

| 服务 | 平时使用 | 测试时改用 |
|---|---|---|
| rustsimhub-core | `rustsimhub-v1/core`（真实管理员、短信、通话） | `rustsimhub-v1/first-setup-test-20261028/core`（空） |
| rustsimhub-setup-edge | `rustsimhub-v1/setup-edge` | 临时目录下的 `setup-edge` |
| rustsimhub-setup-ap | `rustsimhub-v1/system/setup-ap/{installation,journal}` | 临时目录下的 `system/setup-ap/...` |

- 覆盖配置在 `/run` 下，**设备重启就自动消失**，服务回到真实数据。这是最后一道保险。
- 真实数据目录在测试期间不被任何服务挂载，只读核对哈希。
- 日常 edge、媒体、灯控、mDNS、设备名都不改；日常页面在测试期间会连到临时 Core（看到的是空设备），这是预期的。

## 准备（用户在场前即可做，不影响正式服务）

1. 只读检查：确认版本 59、7 个服务正常、没有通话、转发关闭、自动恢复次数未用；记录真实数据关键文件的哈希（身份、管理员、短信库）、NM 已保存的连接列表（UUID）。
2. 建临时目录（root 0700），按正式安装的属主和权限建好 `core/{state,identity,archive,access,compat,journal,setup,setup-ap-journal}`（Core 用户 0700）、`setup-edge`（edge 用户 0700）、`system/setup-ap/{journal}`（root 0700）。
3. 用正式程序在与初装器同款的沙箱里生成临时身份：
   - Core 身份和一次性设置窗口：`rustsimhub-core --prepare-device-ap state identity setup`（以 Core 用户运行，只能看到临时目录）；
   - 配网 edge 安装：`rustsimhub-edge --prepare-setup-local`（edge 用户，临时目录）；
   - 热点材料：`rustsimhub-setup-ap --prepare-from-core <临时>/system/setup-ap <临时>/core/setup <临时>/setup-edge/installation 985 986`。
   临时身份的公钥和设置码只留在设备临时目录，不导出。

## 实测（需要用户在场，约 20–30 分钟，期间设备不能收发短信和电话）

开始前：用户在终端输入 NAS 密码打通 USB 维护通道（热点开启后 Wi-Fi 会断，只能经 USB 观察）。我先启动只读监控。

4. 布置安全网：用 `systemd-run --on-active=45min` 设一个**自动恢复定时器**，到时执行下面的“恢复”步骤（即使我这边断开也会执行）。
5. 停止整组服务（等待全部停止），写入三份运行时覆盖配置，`daemon-reload`，启动整组服务。
6. 临时 Core 发现自己没有管理员，自动开出首次配网热点 **RustSimHub-0087（无密码）**。我经 USB 核对：热点开放、防火墙为开放变体（14/15 行）、DNS 和 8080 可达。
7. 用户用手机连接热点，观察是否**自动弹出配网页**；不弹出时手动打开 `http://192.168.100.1`。
8. 页面上：设置一个**测试用**用户名和密码 → 从列表选家里的 Wi-Fi（或手动输入）→ 试连 → 确认保存。
   - 热点单次最长 5 分钟，到期会自动回到原来的 Wi-Fi，可以再开下一次。
   - 保存会在 NM 里新建一个 Wi-Fi 连接（与已有的家里连接重复）。
9. 每一步的结果、拒绝原因、设备日志都由我经 USB 记录。

## 恢复（测试结束或任何异常时）

10. 停止整组服务 → 删除三份运行时覆盖配置 → `daemon-reload`。
11. 删除测试期间**新增**的 NM 连接（按测试前后的 UUID 对比，只删新增的；原来的家里连接保留）；确认没有残留的配网保护表和热点配置。
12. 启动整组服务，回到真实数据。核对：设备身份公钥与测试前一致、1 个管理员、收件箱 96 条（或测试期间新收到的短信已从模组导入）、7 个服务正常、自动恢复次数未用、Wi-Fi 回到家里的网络、日常页面正常。
13. 取消自动恢复定时器。临时目录保留作证据；之后经用户同意再删除。

**兜底**：恢复脚本失败或连接中断时，自动恢复定时器会执行第 10–12 步；仍不行就重启设备（覆盖配置在 `/run` 下，重启后自动失效），再经 USB 清理新增的 NM 连接。

## 风险与说明

- 测试期间（约 30 分钟）正式 Core 不运行：来电接不到，短信由临时 Core 收进临时库。Core 不会从模组删除短信，恢复后应能由正式 Core 导入，第 12 步会核对；如果数量对不上，会把临时库里的短信导出给用户核对，不会丢弃。
- 热点无密码、http 明文：测试期间附近的人也能连上，家里 Wi-Fi 密码会明文传输一次（用户已接受）。
- “已有一个保存的 Wi-Fi 时保存新 Wi-Fi”这条路径从未实机跑过，可能失败或进入结果不明；按设计会保留证据、不自动重试，经 USB 人工收尾。
- 测试用的用户名密码只对临时身份有效，恢复后无用；当前真实管理员仍是浏览器配对的密钥。

## 需要用户批准的设备操作

建临时目录并生成临时身份（第 2–3 步）；停启整组服务并写入/删除运行时覆盖配置（第 5、10、12 步）；删除测试新增的 NM 连接（第 11 步）；必要时重启设备（兜底）。

## 第一次实测结果（2026-10-29 凌晨 UTC 18:2x，用户在场）

**切换过程中的问题（测试工具，已修）**：Core 的运行时覆盖配置里用空的 `BindPaths=` 清掉原挂载，但 systemd 里 `BindPaths=` 和 `BindReadOnlyPaths=` 共用同一份列表，程序目录的只读挂载也被清掉，启动器找不到 Core，拒绝启动（“service admission refused”）。已用临时测试单元在设备上确认，修正为重新加上程序目录挂载。前两次切换失败时，开始脚本都自动执行了恢复，真实数据随即恢复；但 Core 失败触发了 `OnFailure`，**本次开机的自动恢复次数已被用掉**（重启后重置，版本账本不受影响）。另外一次是我的修补命令没有在出错时停下，导致未修正的版本又跑了一次，同样被自动恢复。

**实测（第三次切换成功后）**：
- 临时身份下 Core 自动开出首次配网热点：**RustSimHub-0087，无加密**，NM 状态 activated；防火墙为开放变体；8080 配网页和 53 DNS 在监听。**开放热点在 wcn36xx 上可以正常工作**。
- 手机连上热点并拿到地址（DHCP 192.168.100.148）。
- **问题 1：手机没有自动弹出配网页**（像公共 Wi-Fi 那样）。从设备上发送的探测请求（Host 为 connectivitycheck.gstatic.com）确实得到 302 跳转到配网页，但手机没有弹出；原因待查（dnsmasq 是否实际加载了通配配置、手机厂商用的探测地址或 https 探测）。
- **问题 2：手动打开 `http://192.168.100.1` 能显示页面，但提示“无法连接设备”**。从设备上用同样的请求测试，接口正常返回；问题出在页面脚本：设备应答带外层 `{protocol,id,result}`，`setup.js` 没有解包。测试用的模拟设备返回的是未包装的结果，所以没发现。已修复：按日常页面的方式核对 `protocol`/`id` 并取 `result`；测试改为真实格式，并确认旧代码会被测试抓到。**未部署**（页面编译在 edge 程序里，需要新版本）。
- **问题 3：首次配网窗口只开一次**。5 分钟到期后两边都写了 closed 记录、防火墙释放、回到原 Wi-Fi（收尾正确），但之后**不会再次开启**。新设备用户错过这 5 分钟就无法配网，需要设计重新开启的方式。
- 恢复：按方案执行，7 个服务回到真实数据，真实身份不变，Wi-Fi 列表与测试前一致，没有失败单元。临时目录保留作证据。

## 第二次实测（应用 60，2026-10-29 UTC 18:57）

- 准备：设备重启后 NAS 一侧的 USB 维护连接需要重新激活（用户在终端输入密码执行）；临时身份的配网 edge 和热点材料用应用 60 的程序重新生成，旧材料保存在临时目录的 `before-app60`。
- 切换到临时身份成功，但**热点没有开出来**：约 1 分钟内出现了 30 个日志文件，即 15 轮首次配网，每轮都在 1 秒内以 `closed`（`rollback_verified=true`、`guard_released=true`、没有拒绝原因）结束，然后立即开下一轮。
- 原因：Root 创建 NM 检查点时，超时只允许 30–330 秒（原来“5 分钟加 30 秒”的残留）。窗口改成 1 小时后，检查点 3630 秒被判为无效，每轮在激活前就收尾。模拟 NM 只认 330 秒，所以测试没发现。
- 处理：立即恢复真实数据（7 个服务、真实身份不变、Wi-Fi 列表一致、Wi-Fi 回到家里网络）。修复：检查点上限跟随 `MAX_WINDOW_SECONDS`（+30 秒），模拟 NM 也改为检查这个范围，新增测试（最长窗口可以，超出 1 秒就拒绝且不调用 NM）；Core 的自动重开限制为每 30 秒最多一次，新增测试（立即关闭的轮次不会紧密循环）。setup-ap 98、Core 165，clippy 干净。**未部署**。

## 第三次实测（应用 61，2026-10-29 UTC 19:12–19:18）

- 切换后热点仍未开启：上次恢复时正好在一轮启动中途停了服务，留下一条只有 intent 没有 closed 的轮次记录。临时 Core 按设计把它当作“结果不明”，一直等 Root 的收尾证明，所以不开新轮。核对 Root 临时日志后确认那一轮 Root 从未接收、从未执行（最后一次 consumed 在它之前），归档这条陈旧记录后重启，热点随即开启：**RustSimHub-0087，无密码，配网页和 DNS 在监听**。
- **自动弹出**：用户换用 Android 手机后能正常弹出配网页；DNS 日志显示小米的联网探测地址（`connect.rom.miui.com`）等都解析到设备地址。第一次没弹出的手机有待确认（可能是 iOS），记为待验证。
- **管理员创建成功**（临时身份 `owner_setup_available=false`），但随后这一轮在 19:17:16 关闭，页面显示“设备暂未开放热点配网”。原因：引导轮次每秒核对一次授权，核对时用 `try_lock` 拿认证锁；页面正在创建管理员或登录时锁被占用，一次“忙”就被当成拒绝，整轮被永久取消；已有管理员后也不会再开新轮。
- 同时发现：每秒发一次保活，序号上限 1024，1 小时的轮次约 17 分钟就会用完序号。
- 用户反馈：附近 Wi-Fi 下拉列表不会自动刷新，也没有刷新按钮。
- 恢复：按方案恢复，核对通过。
- 修复（未部署）：锁忙或设备暂不空闲时只跳过这次核对，只有真正的拒绝才取消；如果一直忙，Root 的心跳超时会收尾，30 秒后重开。保活改为最多每 5 秒一次（1 小时约 720 次）。配网页加“刷新列表”按钮，每 20 秒自动刷新，刷新时保留已选项并显示更新时间。测试：Core 167（新增：锁被占用时不取消；连续快速 tick 不重复发保活），网页测试新增刷新不重复的断言，全部通过；clippy 干净。
