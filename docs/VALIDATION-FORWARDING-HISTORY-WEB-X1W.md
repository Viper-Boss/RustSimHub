## 使用流程

短信转发高级区内折叠“历史短信补发”。管理登录并读取后，选择“最早一批”或本次操作中“继续上一批之后”、1～32条及已有目标，点击预览。页面显示扫描/跳过/已有任务数量、实际递送数量、每条内容模式和回执；记录ID折叠显示。确认前不入队、不打开开关、不启动转发进程。默认内容模式仍由已保存规则决定；预览含完整正文时必须另外勾选并确认。

取消只针对未提交预览。刷新、重登或双标签只核对当前持久记录；结果不明不自动再投。页面不会后台持续轮询。开启总开关会改变代次并取消旧预览，应重新读取和预览；OFF可明确预览，不能确认补发。分页沿用当前真实可见业务列表，回收站、其他SIM、二进制和疑似重复仍排除。

## 防重与保存

Core每个预览生成独立`confirmation_id`；确认、取消和归档均绑定该值。即便用户显式归档后客户端又用了相同请求ID，旧确认或旧取消也不能作用于新预览。批次索引和全部递送同一事务提交，已submitted重放只查询原回执；跨代次Unknown不会自动重建。

浏览器在prepare前先以实际IndexedDB读写事务/CAS保存请求ID、代次；在commit前持久保存确认码和submit_started。只有CAS成功的标签可以提交。归档先保存有限本机摘要，再在网络操作前保存archive_started。登录变化和关闭页面使旧回调失效；存储失败不放行网络提交。

已确认/失败/取消或过期批次，可由最近登录Owner明确归档设备批次索引，原jobs和递送回执保持。queued/in_flight/Unknown不能删除设备索引；网页可明确保存未决摘要后继续，既不删除它也不重投。缺失回执不等于没有发送，需保留不确定摘要。设备最多64个批次索引，本机最多64份摘要；本机只在有已确认摘要可淘汰时腾位，不静默丢未决摘要。页面提供已保存摘要的再次核对入口。

X1V初期格式3元数据如缺确认码，在实际绑定/完整性核对之后，以有限事务补入确认码；旧prepared在重开后过期，旧submitted及Unknown/请求内容保持。旧无确认码的wire命令拒绝。历史API修订2与规则修订2独立，旧页面不会假定支持新补发。业务DB仍schema6，outbox仍格式3；旧格式1/2向前迁移测试保持，完整旧代码/Root回退仍属FWD-20，未据此宣称通过。
