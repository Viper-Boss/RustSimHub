## 1. 产品目标与明确边界

### 1.1 用户最终希望实现

用户通过 Windows 电脑或 Android 手机打开部署在 **GitHub Pages** 的 RustSimHub Configurator 网页：

1. 点击“连接蓝牙设备”，浏览器弹出原生 BLE 设备选择器；
2. 连接附近的 UFI003；
3. **验证设备身份并使用事先授权的恢复客户端身份登录**；
4. 查询有限的设备/网络状态；
5. 填写新 Wi-Fi SSID 和密码；
6. 通过 BLE 触发已有 RustSimHub Core 的 `wifi_begin` → `wifi_status` → `wifi_confirm` / `wifi_cancel` 事务；
7. 看到明确的保存、回滚或结果不明状态；
8. Wi-Fi 恢复后回到现有的 HTTPS 网页管理后台。

USB 可被 One-KVM 用于采集，BLE 配网**不应依赖 `usb0` 已连接**。配网页面只传配置指令，**不通过 BLE 传送 KVM 视频**，也不通过 BLE 暴露短信、电话、系统 shell、任意文件或调试接口。

### 1.2 客户端范围

| 平台 | 第一版策略 |
|---|---|
| Windows + Chrome/Edge | Web Bluetooth + GATT，直接使用 GitHub Pages |
| Android + Chrome | 同一网页，响应式设计，可安装 PWA |
| iPhone Safari/Chrome | **不原生支持 Web Bluetooth**；第一版明确提示不支持，不伪称可用 |
| 微信小程序 / Android APK / Windows EXE | 后续可复用 GATT 协议的可选适配层；第一版**不开发** |

### 1.3 部署策略

- 网页静态资源放入 **`configurator/`**，通过 GitHub Actions 发布 GitHub Pages。
- 预期站点：`https://viper-boss.github.io/RustSimHub/`，**这是预期地址，不是已部署成功的证明**。
- `docs/` 继续保存原工程文档；Pages 使用 GitHub Actions artifact，不直接改写 `docs/`。
- 运行时不需要云端数据库、VPS、付费域名、App Store 开发者账号。
- GitHub Pages 只负责提供 HTML/JS/CSS；**蓝牙通讯是本机浏览器与 UFI003 点对点完成**，不经 GitHub 中转。
- 用 Service Worker 预缓存离线页面，确保曾成功安装/缓存的页面在 Wi-Fi 故障或互联网不可用时仍能打开。不得宣称首次访问即可离线使用，也不得假设浏览器清缓存后仍可打开。

## 2. 实际源码基线：已知能力与必须处理的问题

已读取的现有实现有：

- `crates/core/src/network_trial/provision.rs` 已有 `WifiBegin`、`WifiStatus`、`WifiConfirm`、`WifiCancel`、`OwnerGate`、40 秒 Core 截止、45 秒 NetworkManager checkpoint、volatile 候选配置、确认保存、出错补偿和 `Unknown` 状态。
- `crates/core/src/network_trial.rs` 的 `NetworkManager::snapshot_inner(true)` 当前同时要求可用 `wlan0` **和已连接的 `usb0`**；`fence()` 还会验证 USB 活动 profile。**只去掉一个 usb 检查仍会失败。**
- `provision.rs::owner()` 当前要求 `recent_owner()` 与 `Scope::NetworkManage`，不能让普通蓝牙配对或任意 `Kind::Client` 绕过这一约束。
- `crates/core/src/authenticated.rs` 分发 Wi-Fi 命令，现有 Core 通过受限 Unix socket 通信，执行端有 UID/peer 检查。
- `crates/wire/src/auth.rs` 使用严格的 `AuthCommand` 枚举与 `deny_unknown_fields`；请求帧大小有上限。
- `crates/auth/` 使用 Ed25519 身份、challenge、generation、会话/撤销等机制；Owner 只有一个，不应制造第二个 Owner。
- `docs/platform-runtime.md` 明确网络操作共用锁并与电话状态协调，必须保留。
- `docs/PROGRESS-SCALE.md` 与 `docs/HANDOFF.md` 记录 Wi-Fi 独立 HTTPS 网页已有真实设备验证；**BLE 尚未据此证明可用。**

由此确定开发策略：**扩展同一个 Core 的有限配网能力，而不是构建另一个有完整系统权限的蓝牙后台。**

### 2.1 USB 门禁重构（必须强类型、不可简单删安全检查）

设计带明确信任来源的通道类型，例如：

```rust
// 设计示意；请按当前源码实际类型调整，不是可直接复制的补丁。
enum ProvisionChannel {
    UsbTrusted,
    BleRecovery { principal_id: String, grant_generation: u64 },
}
```

- 原 HTTPS/USB 流程的 Owner、USB、NM、MM、语音空闲和 WWAN 栅栏**保持原语义**。
- BLE 通道只有在**独立 BLE 授权和证明**通过后，才能不依赖 `usb0`；不得将前端输入的 `channel="ble"` 当作有效安全证据。
- BLE 通道继续验证固定 `wlan0`、设备类型、NM/MM 唯一 D-Bus owner、活动通话状态、WWAN/普通蜂窝自动连接边界、网络独占锁与现有 profile 身份。
- 在 `begin`、后台轮询、`confirm` 和保存完成后均重新验证恢复授权/generation，撤销后拒绝继续保存。
- 不在 USB Host 模式下假造一个“已连接 usb0”以通过现有检查。
- 修改前增加失败路径回归，分别验证无 USB + 未认证 BLE 拒绝、无 USB + 认证 BLE 允许、原 USB 路径行为不变。

## 3. BLE 硬件前置门槛：先探测、再实现

**不能只因 MSM8916 芯片家族支持蓝牙就断言 UFI003_MB_V02 具备可用 BLE 外设与天线。** Codex 先核对设备树、内核配置、固件路径、BlueZ 能力以及可用的实机只读证据。

建议仅做只读或离线检查：

```sh
uname -r
ls -la /sys/class/bluetooth/ 2>/dev/null || true
bluetoothctl list 2>/dev/null || true
btmgmt info 2>/dev/null || true
zcat /proc/config.gz 2>/dev/null | grep -E 'CONFIG_BT(_QCOMSMD|_QCA)?=' || true
lsmod | grep -Ei 'btqcomsmd|bluetooth|btqca' || true
dmesg | grep -Ei 'bluetooth|wcnss|btqcomsmd' | tail -n 40 || true
```

进一步验证：

- 是否存在 `hci0`，设备 HCI 实际是否 `Powered`；
- 是否支持 **LE Peripheral / Advertising**，而不只是 BLE Central；
- `org.bluez.GattManager1`、`org.bluez.LEAdvertisingManager1` 是否可注册本地服务和广播；
- 板载 RF/天线是否真实可供 Windows/Android 扫描与连接；
- WCNSS Wi-Fi 和蓝牙是否共享故障域，是否可能 Wi-Fi 崩溃时同时失去 BLE；
- BLE 实验是否影响现有已稳定的 Wi-Fi、电话、短信、基带固件。

**硬件不满足时必须明确报告阻塞：** 停止以“内置蓝牙可用”为前提的部署，不擅自刷基带、设备树或 NV；可先完成独立 mock GATT 后端和静态网页，但标为“离线实现，未验证硬件”。

## 4. 服务端架构：BlueZ GATT + 受限 Core IPC

建议新增：

```text
crates/ble/
  Cargo.toml
  src/main.rs
  src/gatt.rs
  src/advertisement.rs
  src/protocol.rs
  src/secure_session.rs
  src/core_client.rs
  src/state.rs
  src/tests.rs               # 可以拆为 tests/ 下的集成测试
```

名称可按仓库现有组织调整。Rust service 建议命名为 `rustsimhub-ble`。

- 通过 BlueZ **D-Bus GATT Server** 暴露自定义服务，通过 LE Advertising 对外广播。
- 使用固定、版本化的自定义 Service UUID/Characteristic UUID；一次生成并提交协议常量，不在每次运行时随机更换服务 UUID。
- 低权限专属服务用户、最小 systemd 和 D-Bus 权限、合理的内存/连接/广播预算。
- 服务**不能**读 Core identity seed、业务 SQLite、短信数据库、NetworkManager 私有连接文件、设备完整密钥或配置文件；它只向专用受限 Core IPC 发送白名单命令。
- **不能**单纯把现有 HTTPS `/api/v2` 的全部 `AuthCommand` 不加筛选地透传到 BLE。使用独立、最小 API 或严格的映射层，明确拒绝 SMS/电话/Owner 恢复/OTA/任意命令。
- 如果现有 Unix socket 只允许单一 UID，新建**独立 BLE 限权 socket / 受限适配器**，经 `SO_PEERCRED` 核对特定 BLE 服务 UID，而不是将蓝牙服务 UID 加进可以操作全部业务的通道。
- BlueZ 不可用时 RustSimHub Core/Edge 仍能正常启动和运行，BLE 不得成为电话/短信服务的硬依赖。

### 4.1 GATT 接口（建议四个 characteristic）

| 特征值 | GATT 属性 | 内容边界 |
|---|---|---|
| DeviceInfo | Read | 协议版本、有限匿名能力；不含 IMEI/IMSI/MAC/手机号/SSID/秘钥 |
| AuthExchange | Write / Notify | 客户端密钥挑战、设备身份签名、会话确认 |
| Command | Write | **认证加密后的**白名单请求，包括 Wi-Fi 事务 |
| Result | Read / Notify | 带请求 ID 的状态、错误、会话限时；不回显密码 |

提供独立、版本化 GATT 协议文档，如 `docs/ble-recovery-protocol.md`。

### 4.2 传输与错误恢复

- 不假设 ATT MTU 固定大小，做严格有界的分片、重组、序号、总长度、超时与错误处理；应考虑小 MTU（例如 23 字节 ATT MTU 时通常很小的特征值有效负载）。
- 每条操作含 `request_id` / 单次随机 nonce 和确定性响应状态；重复写入不能重复执行 Wi-Fi 修改。
- BLE 断连后不能擅自重放 `wifi_begin` 或 `wifi_confirm`；重新连接须重新认证，并查询可能保留的事务结果。
- 对 `Unknown` 保留原有不自动重试的原则；对回滚结果不能伪称已成功。
- 操作长时间运行要通过 Notify 推送状态；不得在单次 GATT 写处理回调中阻塞几十秒。
- 速率限制、单会话/操作并发上限、最大输入尺寸、日志脱敏、及时清零凭据缓冲。

## 5. 安全协议：预注册的 BLE 恢复身份，不要求重做 Owner

### 5.1 首次绑定（必须在已有可信管理方式可用时完成）

正常通过 Wi-Fi/已有受信任 USB 访问 RustSimHub 后台时：

1. 已有 Owner **最近重新认证**；
2. 用户点击“启用 BLE 应急恢复”，明确授权；
3. Configurator 浏览器为该设备生成**独立的恢复客户端密钥对**（不导出当前网页 Owner 私钥，不复制它到另一个 GitHub Pages origin）；
4. 由 Owner 在可信管理通道批准该恢复公钥，仅赋予 `wifi.recovery` 类的狭窄能力；
5. 记录生成时的设备身份 pin/公钥指纹，用户必须通过已受信任渠道验证；
6. 用户须在断网前至少成功测试一次 BLE 认证，明确告知若未预绑定，则不能靠未知 BLE 设备在断网后自动成为 Owner。

如需新增“BLE 恢复授权”存储，使用受控 schema 迁移，维护原 `principal/generation/revocation` 语义；尽量不改变旧 scope bit 含义。**不要通过把 `Kind::Client` 伪造成 Owner 或赋予 `network.manage` 全权限来实现应急配网。**

网页密钥存储应使用浏览器 WebCrypto 非导出型私钥和 IndexedDB；恢复授权应可由 Owner 撤销。浏览器清理数据导致密钥丢失时，必须重新由 Owner 在可信通道绑定，不能降级为空口令恢复。

### 5.2 会话安全

- BLE pairing/bonding 不是充分的业务授权。业务层应单独验证预登记的客户端公钥/授权代次、设备公钥和签名挑战。
- 对 Wi-Fi SSID/密码及指令使用**经身份绑定的端到端加密会话**：推荐标准化、可审查的临时 ECDH + HKDF + AEAD（如 AES-GCM），设备签名绑定双方临时密钥、nonce、设备身份、协议版本与会话上下文；浏览器端检查支持后再使用。
- 先验证浏览器 WebCrypto 算法可用性；不自行设计不成熟密码学，也不把单纯“自定义混淆/固定 AES 密钥”视为加密。
- AEAD nonce 在同一 key 下不能复用，明确消息方向、独立计数器、重放窗口和 Associated Data。会话过期或断线需重新握手。
- `DeviceInfo` 只放最少匿名内容；不经认证不能读取完整网络状态、设备身份信息或可管理接口。
- 开启广播需有限配对窗口/授权控制，不能永久公开一个未经认证的重置/改 Wi-Fi 通道。
- 身份撤销要立即影响进行中尚未持久提交的操作，不能用先前已通过一次的 BLE 连接长期持有授权。

### 5.3 首次设置和紧急情况

- 目前生产设备**已经有唯一 Owner 和正式身份**。不可重复打开或重跑原一次性 Owner setup helper。
- 如果设备从未登记过 BLE 恢复密钥又失去 Wi-Fi，第一版应说明仍需已有可信维护途径；不能在没有物理凭据的情况下匿名接管设备。
- 后续如设计按键/物理证明的应急绑定，必须独立威胁建模和硬件验收；不能把 UFI003 既有恢复/9008 按键语义随意当作授权按钮。

## 6. Core Wi-Fi 事务复用与状态机要求

复用现有 `wifi_begin/status/confirm/cancel` 底层引擎与事务锁，并添加一个只允许已授权 BLE 恢复身份调用的桥接层。

要求：

1. **唯一活动 Wi-Fi 事务**：现有网页与 BLE 配网同时发起时，遵循统一互斥策略，失败时明确 Busy。
2. **USB 门禁分开**：正常模式行为不变；BLE 模式凭已验证的恢复能力允许 `usb0` 不存在或未连接；其他栅栏不能删除。
3. **保护真实语音状态**：继续验证活动通话、NM/MM owner 和电话控制协调锁，不能因为应急配网而中断业务。
4. **不启用蜂窝回退**：不允许隐式建立/激活普通 APN，不更改 `WWAN/IMS` 射频状态，不创建任意蜂窝连接。
5. **严格 Wi-Fi 设置白名单**：沿用当前 `wlan0`、SSID 长度、WPA2-PSK 合法性及显式 IPv4/IPv6 配置范围；后续 WPA3 要独立设计和验收，不在第一版扩大范围。
6. **现有 NM checkpoint 语义保留**：原 Core 40 秒期限 / NM 45 秒回滚；不全局 DestroyAll、不能删除其他连接、失败时只补偿自己的候选。
7. **避免竞态**：`ready` 只表示候选 AP/IPv4 通过，不表示互联网可达；`confirm` 才写入持久配置；未知保存结果继续显示 Unknown。
8. **认证复核**：在开始/确认/保存前、NM owner 变更、BLE 断连/撤销等情况下按明确状态策略检查，不能对意外超时自动再提交。
9. **保留权限边界**：BLE 只做有限状态与配网，原 `network.manage` 网页权限、短信/电话权限与其他业务不受影响。
10. **崩溃安全**：对同一幂等 key 在进程重启后是否已提交给出可查询或 Unknown 结果，确保不会二次写网。

建议的 BLE 白名单：`device_info`、`network_summary`、`wifi_begin`、`wifi_status`、`wifi_confirm`、`wifi_cancel`、`disconnect`。不提供 shell、APN、SIM、SMS、通话、升级、Owner 重置、通用参数写入。

具体命名可调整，但**不要依赖任何需在线加载的运行时 CDN**（脱机页面不能从 CDN 获取 JS/CSS）。尽量用原生 JS/CSS，不额外安装沉重的前端框架。

### 7.1 功能页面

- 浏览器兼容性检测：`navigator.bluetooth`、HTTPS 安全上下文、必要 WebCrypto 能力；不支持时给出明确说明。
- “连接 UFI003”按钮：在**用户点击事件**中调用 `navigator.bluetooth.requestDevice()`，按固定服务 UUID 或经过评估的设备名过滤，并使用 `optionalServices` 获取 GATT 自定义服务。
- 设备识别：验证设备签名和本地保存的可信设备 pin；禁止仅凭广播名称直接显示“安全”。
- 恢复身份管理：显示“未授权/已授权/已撤销/需要重新绑定”，不展示私钥、恢复 token。
- Wi-Fi 配置：SSID/密码输入、输入校验、提交、状态轮询/Notify、明确确认、取消和失败处理。
- 状态页：协议版本、匿名能力、已认证后的网络连接摘要、候选事务结果；不展示完整敏感设备信息。
- 回到后台：展示实际验证得到的设备 HTTPS 地址或已保存的可信入口；不自动跳过证书校验或信任未知 URL。

### 7.2 PWA 离线关键点

- 只缓存公开的 HTML/JS/CSS/manifest/图标；**绝不缓存 Wi-Fi 密码、解密的协议指令、蓝牙密钥或会话数据**。
- 使用明确版本的预缓存列表及更新提示；静态站点部署在 `/RustSimHub/` 子路径时，manifest `start_url/scope` 与 SW 注册使用相对路径，不能误写为 `/` 导致 404。
- 手机/电脑首次访问需联网、成功加载/安装后再可离线打开；不承诺首次离线打开。
- 页面被刷新或关闭时处理蓝牙断线和事务状态，不能因页面刷新自动重试有副作用的操作。
- 密码 input 不做 localStorage/IndexedDB 持久保存；提交后及时擦除 UI 状态（浏览器内存不保证完全物理清零）。
- 设置基本 CSP、限制脚本来源和第三方资源；禁用跨站不受控内容。
- GitHub Pages **不是后端**；不能把设备密码发给 GitHub API、任何 analytics、日志或服务端。

## 9. 需要的验证矩阵（离线优先）

### 9.1 单元与集成测试

至少覆盖：

- BLE GATT 命令校验：非法 UUID / op / 长度 / 分片序列 / 截断 / 重放 / 非法 nonce / 认证失败；
- 设备身份签名不匹配、未登记客户端、已撤销客户端、generation 改变、会话过期、签名重放；
- 未认证/普通客户端无法触发 `wifi_begin`；BLE 认证成功但无恢复授权仍拒绝；
- `usb0` 不存在时原 USB 网页配网拒绝，而合法 BLE 恢复路径可通过；
- `usb0` 存在时原有 USB 路径无行为回归；
- Wi-Fi 错误密码、AP 消失、DNS/IPv4 不可用、设备 Busy、NM owner 变化、MM 有活动通话、已有 checkpoint、WWAN 策略异常；
- `confirm` 前后权限撤销、断连、Core 崩溃、BlueZ 崩溃、NM 崩溃与假阳性 Ready；
- 重复提交同一幂等 key、未知状态不重试、取消/超时只删除自己的候选；
- GATT 客户端连续断连/重连、页面刷新、浏览器重启、PWA 离线打开、缓存升级；
- 回归 Rust Core 的短信、通话、媒体、Owner、更新、网络守卫和原现有网页功能。

### 9.2 真机验收（必须另行授权，不是本任务自动执行）

先只读探测，再分阶段：

1. UFI003 BLE 广播能被 Windows/Android 正常扫描到；
2. 设备身份固定可信、公钥核验和恢复客户端配对成功；
3. USB NCM 在线时不影响现有网页/电话/短信；
4. USB NCM 不在线且 Wi-Fi 断开时，已绑定客户端能通过 BLE 完成 Wi-Fi 重新配置；
5. 错误密码 45 秒内正常回滚，不启动普通蜂窝数据；
6. 蓝牙断线/重启/恢复客户端撤销可安全结束操作，不能偷偷续写；
7. Wi-Fi 恢复后 HTTPS 后台正常登录，身份、证书、Owner、短信、电话及持久配置不变；
8. KVM Host 模式另行验收 USB 电源/PHY，**不与 BLE 变更一起刷内核或切 USB 模式**。

### 9.3 完成定义

- **离线实现通过**：新增服务/网页与测试在模拟环境通过，并明确列出硬件待测项；不可标成“已经能应急配网”。
- **BLE 硬件通过**：真实 HCI、LE Advertising、GATT Server 与 Windows/Android 互操作证据通过。
- **BLE 应急配网通过**：无 `usb0` + Wi-Fi 断开的真实场景，已授权手机/电脑能安全配网、失败能回滚，且旧业务不受影响。
- **Pages 上线通过**：GitHub Actions 成功、真实 HTTPS 站点打开、浏览器 BLE 手势授权、PWA 离线加载测试通过。

不得把其中一个完成状态替代其余状态。
